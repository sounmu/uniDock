# 다중 대학 LMS 지원 원칙

상태: 합의된 설계 방향. 현재 구현 완료나 이화여대 연동 검증을 의미하지 않는다.

## 목표

고려대에 이어 이화여대와 다른 대학에서도 기존 기능 전체를 지원한다.
학교 추가 시 공통 화면, 일정, 알림을 수정하지 않고 학교 설정과 필요한 연동 구현을 추가하는 것을 목표로 한다.
이화여대의 LMS 제품, API, 인증 방식은 실제 환경에서 확인하기 전까지 가정하지 않는다.

## 코드 경계

| 영역 | 책임 |
| --- | --- |
| 공통 앱 | 화면, 일정, 알림, 검색, 저장, 변경 감지, 동기화 흐름 |
| 공통 LMS 계약 | 과목·공지·과제·학습 상태의 의미, 명령, 결과, 오류 |
| LMS 어댑터 | 제품별 요청, 페이지네이션, 응답 변환, 작업 실행, 오류 변환 |
| 학교 설정 및 특수 구현 | 학교 식별자, 도메인, 어댑터 선택, 로그인 연결, 확인된 학교별 예외 |

대학과 LMS 제품은 별개로 취급한다. 같은 제품을 쓰는 대학은 어댑터를 재사용하고,
설정으로 표현되지 않는 실제 동작 차이만 학교별 구현으로 분리한다.
공통 화면과 업무 로직에 학교 이름에 따른 분기를 흩뿌리거나 대학별 앱을 복제하지 않는다.
구체적인 디렉터리와 인터페이스는 기존 코드 및 두 학교의 실제 동작을 비교한 뒤 결정한다.

## 공통 계약의 범위

입출력 JSON 모양뿐 아니라 의미와 완료 조건도 동일해야 한다.

- 식별자는 학교·계정·외부 ID의 범위를 구분한다. 다른 학교의 같은 ID가 충돌하면 안 된다.
- 시간대와 마감일 부재를 명시한다. 조회 실패를 마감일 없음으로 바꾸지 않는다.
- 제출 여부, 지각 여부, 학습 완료, 출석 인정은 의미를 확인하고 구분한다.
- 목록의 전체 조회 여부와 다음 페이지를 명확히 표현한다.
- 쓰기 요청 접수와 실제 완료를 구분한다.
- 로그인 만료, 권한 없음, 데이터 없음, 일시 실패, 미지원은 구분한다.
- 미구현 기능을 빈 목록이나 성공으로 반환하지 않는다.

기존 기능 전체 지원이 목표다. 특정 LMS의 API에 기능이 없으면 다른 접근 경로를
검토하고 미해결 사항을 명시한다. 지원 목표를 조용히 축소하지 않는다.
Canvas 응답을 그대로 공통 모델로 삼지 않고 두 학교의 의미를 비교해 계약을 정한다.

## 사용자가 준비할 자료

기존 기능 목록 각각에 아래 양식을 채운다. API 명세 작성은 사용자에게 요구하지 않는다.

```text
기능:
이화여대 화면 / 접근 경로:
확인 가능한 과목과 항목:
사용자가 하는 동작:
정상 처리 후 표시되는 결과:
상태 표시의 의미:
특이사항:
확인하지 못한 부분:
```

로그인 진입점, 추가 인증, 직접 로그인이 필요한 단계도 정리한다.
재제출, 지각 제출, 팀 과제, 마감일 없는 과제 등 실제 발견한 예외를 포함한다.
확인할 사례가 없는 기능은 정상 동작으로 간주하지 않고 미확인으로 남긴다.
공유 자료에서 비밀번호, 쿠키, 토큰, 학번, 이름을 제거한다.

개발 측은 접근 가능한 환경에서 엔드포인트, 파라미터, 페이지네이션, 응답 매핑을 분석한다.
사용자 로그인 환경에 접근할 수 없을 때만 필요한 네트워크 자료를 구체적으로 요청한다.

## 자막 연동 경계

학교별 강의·영상 식별과 접근, 플레이어 연결은 확장 연동 영역에서 해결한다.
자막 백엔드에 학교별 로그인이나 화면 해석을 넘기지 않는다.
미디어 및 결과 계약, 식별자와 캐시 경계는
`unidock-captions/docs/MULTI-UNIVERSITY.md`의 원칙과 함께 변경한다.

## 도입과 검증

1. 기존 기능 전체를 목록화하고 학교별 화면·사례·미확인 항목을 연결한다.
2. 고려대와 이화여대 동작을 비교해 공통 계약을 정한다.
3. 고려대 구현을 해당 경계로 분리하고 이화여대 연동을 추가한다.
4. 모든 어댑터에 공통 계약 테스트를 적용하고 학교별 실제 환경에서 검증한다.
5. 기존 고려대 동작 회귀, 로그인 만료, 오류, 식별자 충돌을 확인한다.

단계별 구현 순서는 정할 수 있지만 전체 기능의 검증이 끝나기 전에는 전체 지원으로 표시하지 않는다.
